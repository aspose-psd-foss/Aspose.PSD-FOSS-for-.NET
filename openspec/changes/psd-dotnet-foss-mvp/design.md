## Контекст

**Текущее состояние:**
- Aspose.PSD — коммерческая закрытая .NET библиотека для работы с файлами PSD
- Она предоставляет комплексную поддержку PSD, включая рендеринг, эффекты, текст и т.д.
- Легкой полностью open-source альтернативы для базовых операций с PSD не существует

**Ограничения:**
- НЕ включать рендеринг (без манипуляций с пикселями, без экспорта изображений)
- НЕ включать продвинутые функции (эффекты, smart filters, рендеринг текста)
- Быть standalone-библиотекой, без сложного dependency injection или фабрик
- Сохранять неизвестные section как raw bytes

**Заинтересованные стороны:**
- Open-source разработчики, нуждающиеся в базовых операциях с файлами PSD
- CI/CD пайплайны, требующие валидации/инспекции PSD
- Простые конвертеры и обработчики файлов PSD

## Цели / Нецели

**Цели:**
- Минимальный, чистый API, соответствующий распространённым use-case PSD
- Простая реализация, напрямую следующая спецификации PSD
- Без рендеринга, манипуляций с пикселями или продвинутых эффектов
- Сохранение всего содержимого файла при сохранении (без потерь данных)

**Нецели:**
- Не полноценный редактор PSD (без рендеринга, эффектов, векторных путей)
- Не полная реализация формата (может не поддерживать все функции PSD)
- Без поддержки всех цветовых пространств или глубины бит (фокус на распространённых: 8/16-бит RGB/CMYK)
- Без undo/redo, истории или управления состоянием документа
- Без многопоточной обработки или кэширования

## Решения

### Решение: Прямая реализация PSD спецификации
**Почему:** Вместо копирования архитектуры Aspose.PSD (которая включает фабрики, сервис-локаторы, кэширование, рендеринг и т.д.), реализовать только минимум, необходимый для MVP-сcope.

**Рассмотренные альтернативы:** Зеркальное копирование архитектуры Aspose.PSD с фабриками, сервисами, сложными иерархиями наследования.

**Почему выбрано:** Простота проектирования, лёгкость поддержки, отсутствие ненужной сложности для MVP.

### Решение: Сохранение неизвестных section как raw bytes
**Почему:** Чтобы избежать потери данных при сохранении файлов с неизвестными или неподдерживаемыми section.

**Реализация:** Чтение заголовков и данных неизвестных section, хранение как byte arrays, запись без изменений при сохранении.

### Решение: Только чтение для немодифицированных свойств
**Почему:** Минимальный API должен предоставлять свойства, такие как Width, Height, Name и т.д., без необходимости полного парсинга всех PSD section.

**Реализация:** Базовый парсинг заголовка для свойств документа, ленивый парсинг слоёв только при доступе к коллекции Layers.

### Решение: Без инфраструктуры рендеринга
**Почему:** Рендеринг требует сложного управления цветами, обработки эффектов, композитинга слоёв и т.д., что значительно выходит за scope MVP.

**Реализация:** Без обработки пиксельных данных изображений, без экспорта в другие форматы, без генерации миниатюр.

### Решение: Простой public API, соответствующий конвенциям Aspose.PSD
**Почему:** Familiarity снижает порог входа, даже если API упрощён.

**Пример:**
```csharp
PsdImage.Load("input.psd")
image.Width, image.Height
image.Layers[0].Name = "New Name"
image.Save("output.psd")
```

### Использование reference implementation
**Источник reference кода:** `/Users/sid/Source/net/Aspose.Psd/src/Aspose.FileFormats/Psd/`

**Что использовать из reference:**
- Только observable behavior (что читается/пишется, а не как)
- Только public API signatures и их семантика
- Правильный порядок полей в PSD структурах
- Правильное смещение битов для флагов и полей

**Что НЕ использовать:**
- НЕ переносить внутреннюю архитектуру (фабрики, сервис-локаторы, DI)
- НЕ переносить сложные абстракции (千层接口继承)
- НЕ переносить оптимизации (кэширование, lazy loading сложных структур)
- НЕ переносить know-how и проприетарные алгоритмы
- НЕ переносить рендеринг, эффекты, работа с пикселями

**Основной принцип:** Реализовать структурно корректный парсер/пишер PSD, основываясь НА PSD спецификации и проверяя по reference implementation как ЧИТАЕТСЯ файл, а НЕ копируя код.

### Решение: Минимальная иерархия исключений
**Почему:** Упростить обработку ошибок для MVP.

**Реализация:** Базовые исключения: PsdLoadException, PsdSaveException, FileNotFoundException, ArgumentNullException.

### Решение: Stream-based I/O
**Почему:** Предоставляет гибкость для file paths, in-memory streams, network streams и т.д.

**Реализация:**
- Load(string filePath) и Load(Stream stream)
- Save(string filePath) и Save(Stream stream)

### Решение: Немутабельный header после загрузки
**Почему:** Header должен быть read-only после загрузки для предотвращения повреждения.

**Реализация:** Свойства header доступны только для чтения, модифицировать можно только содержимое файла.

## Риски / Компромиссы

**Риск: Ограниченная поддержка формата PSD** → Mitigation: Фокус на распространённых функциях PSD, соответствующих MVP scope. Явное документирование неподдерживаемых функций.

**Риск: Неполная поддержка PSB (большие файлы)** → Mitigation: PSB — версия > 6, структура та же, что и у PSD. Базовая поддержка должна работать корректно, если ограничения размера в header обрабатываются правильно.

**Риск: Неизвестные типы ресурсов не сохраняются** → Mitigation: Все неизвестные ресурсы должны читаться как byte arrays и писаться без изменений. Документировать, какие типы ресурсов парсятся.

**Риск: Неточность свойств слоёв** → Mitigation: Парсить только то, что необходимо для минимального API. Документировать, какие свойства слоёв поддерживаются.

**Риск: Проблемы производительности с большими файлами** → Mitigation: Считывать только необходимые данные, избегать загрузки всех пиксельных данных (raster) в память. Это допустимо для минимального scope.

**Риск: Ошибка в парсинге section влияет на все файлы** → Mitigation: Гибкая обработка некорректных данных. Попытка продолжить чтение даже если некоторые section некорректны.

**Риск: Изменение размера файла при сохранении** → Mitigation: При изменении длины имён слоёв обновлять все последующие offset. Это сложно, но необходимо.

## Открытые вопросы

1. Следует ли поддерживать PSB (формат больших документов) явно или позволить работать неявно через PSD код?
   - **Решение:** Поддержка неявно (PSB имеет ту же структуру, различаются только ограничения размеров)

2. Насколько подробными должны быть сообщения об исключениях?
   - **Решение:** Базовые сообщения для MVP, расширение при запросах пользователей

3. Следует ли экспонировать свойство ChannelsCount?
   - **Решение:** Да, полезные метаданные

4. Следует ли поддерживать 32-битные PSD файлы с плавающей точкой?
   - **Решение:** Поддержка чтения, но сохранение может завершиться ошибкой — документировать как известное ограничение

5. Какие режимы смешивания (blend modes) поддерживать?
   - **Решение:** Поддержка всех значений enum BlendMode, но парсинг только ключа режима смешивания (4 байта)
   - Полный парсинг эффектов вне scope

6. Группы слоёв (folder layers)?
   - **Решение:** Экспонировать как Layer instances, сохранять структуру групп прозрачно
   - Без специального API для групп в MVP
